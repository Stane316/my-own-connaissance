# **0\. MISSION DU DOCUMENT**

Le SEO est souvent réduit à :

« mettre des mots-clés sur un site ».

La Web Performance est souvent réduite à :

« faire charger le site rapidement ».

Ces deux visions sont beaucoup trop limitées.

Un produit Web peut être :

- magnifique mais invisible ;
- visible mais lent ;
- rapide mais inutile ;
- indexé mais mal compris ;
- bien positionné mais incapable de convertir ;
- excellent sur Google mais absent des systèmes génératifs ;
- techniquement parfait mais sans demande réelle ;
- très visité mais commercialement inutile.

Le véritable problème est donc plus large :

**Comment faire en sorte qu’un contenu soit découvrable, accessible, compréhensible, indexable, pertinent, visible, cliquable, performant, utile et mesurable ?**

Et une seconde question devient de plus en plus importante :

**Comment faire en sorte que ce contenu soit suffisamment clair, fiable, spécifique et utile pour être également utilisé comme source par des systèmes de recherche et d’IA ?**

# **A — VUE GLOBALE : QU’EST-CE QUE LE SEO ?**

## **A.1. Définition**

SEO signifie :

**Search Engine Optimization**

ou :

**optimisation pour les moteurs de recherche.**

Le SEO consiste à améliorer les caractéristiques d’un site ou d’un contenu afin que les moteurs de recherche puissent :

1.  découvrir le contenu ;
2.  accéder au contenu ;
3.  comprendre le contenu ;
4.  déterminer sa pertinence ;
5.  éventuellement le présenter aux utilisateurs ;
6.  offrir une bonne expérience lorsqu’ils arrivent sur la page.

# **A.2. Le SEO n’est pas « tromper Google »**

Une mauvaise conception du SEO consiste à imaginer :

Je connais l'algorithme  
↓  
Je trouve une faille  
↓  
Je manipule le classement

Une approche plus saine est :

Je comprends mon utilisateur  
↓  
Je comprends son intention  
↓  
Je produis une réponse réellement utile  
↓  
Je rends cette réponse compréhensible  
↓  
Je rends mon site techniquement accessible  
↓  
Je mesure  
↓  
J'améliore

Le SEO devient alors une discipline de **qualité + découvrabilité + compréhension + distribution**.

Le SEO peut être divisé en plusieurs grandes catégories.

- expertise ;

## **4\. SEO off-page**

## **5\. SEO local**

# **A.4. SEO ≠ publicité**

SEO :

Trafic organique

Publicité :

Trafic payé

Exemple :

Google Search  
<br/>\[Annonce sponsorisée\]  
\---------------------  
\[Résultat organique\]  
\[Résultat organique\]  
\[Résultat organique\]

Le référencement naturel ne consiste donc pas simplement à acheter de la visibilité.

# **A.5. SEO ≠ Google Analytics**

C'est une distinction essentielle.

### **Search Console**

Répond principalement à :

**Comment Google Search voit-il et présente-t-il mon site ?**

### **Google Analytics**

Répond principalement à :

**Que font les utilisateurs lorsqu'ils arrivent sur mon site ou mon application ?**

Les deux sont complémentaires.

# **A.6. SEO ≠ performance**

Une page peut être :

- rapide mais mal ciblée ;
- lente mais extrêmement pertinente ;
- parfaitement indexée mais sans contenu intéressant.

La performance est **une composante de la qualité globale du produit**, pas l'intégralité du SEO.

# **B — COMPRENDRE LES MOTEURS DE RECHERCHE**

C'est ici que commence réellement la compréhension.

# **B.1. Le cycle fondamental**

Un moteur de recherche doit généralement :

DÉCOUVRIR  
↓  
CRAWLER  
↓  
RENDRE / ANALYSER  
↓  
INDEXER  
↓  
COMPRENDRE  
↓  
CLASSER  
↓  
PRÉSENTER

Ces étapes ne sont pas synonymes.

# **B.2. Crawling**

Le **crawling** est l'exploration des URLs par les robots des moteurs.

Google utilise notamment Googlebot pour explorer le Web.

Le crawler peut découvrir une URL grâce à :

- un lien ;
- un sitemap ;
- une autre référence ;
- des signaux externes.

# **B.3. Indexation**

Une page découverte n'est pas automatiquement indexée.

Indexation signifie, simplifié :

le moteur a traité le contenu et l'a potentiellement intégré à son index.

Donc :

Découverte ≠ Indexation

# **B.4. Classement**

Même une page indexée ne garantit pas qu'elle apparaîtra devant les autres.

Le moteur doit déterminer :

quelle réponse est la plus pertinente pour une requête donnée ?

C'est le classement.

# **B.5. SERP**

SERP signifie :

**Search Engine Results Page**

C'est la page de résultats du moteur.

Elle peut contenir différents types d'éléments :

- résultats organiques ;
- annonces ;
- images ;
- vidéos ;
- cartes ;
- résultats locaux ;
- snippets ;
- fonctionnalités enrichies ;
- éléments génératifs selon le contexte.

# **B.6. Résultat organique**

Un résultat organique peut être représenté conceptuellement par :

Titre  
URL / fil d'Ariane  
Description / snippet

Mais Google ne garantit pas de reprendre exactement le contenu que tu as écrit pour chaque élément d'affichage.

# **B.7. Title**

Le &lt;title&gt; fournit le titre du document HTML.

Exemple :

&lt;title&gt;  
Restaurant africain à Calavi | Nom du restaurant  
&lt;/title&gt;

Il est important pour :

- compréhension du document ;
- affichage dans les résultats ;
- navigateur ;
- partage selon certains mécanismes.

Mais :

le title n'est pas une commande disant à Google exactement ce qu'il doit afficher.

# **B.8. Meta description**

Exemple :

<meta  
name="description"  
content="Découvrez notre restaurant africain à Calavi : menu, horaires, localisation et réservation."  
\>

La meta description sert notamment à fournir une description potentielle du contenu.

Mais :

**Google peut choisir un autre extrait du contenu pour le snippet.**

Donc écrire une meta description ne signifie pas :

« Google affichera obligatoirement cette phrase. »

# **B.9. Snippet**

Le snippet est l'extrait présenté dans le résultat.

Il est généré à partir du contenu et peut varier selon :

- requête ;
- page ;
- contexte ;
- système d'affichage.

C'est important parce que :

**le résultat de recherche est dynamique.**

# **B.10. CTR**

CTR signifie :

**Click-Through Rate**

Formule :

CTR =  
clics / impressions × 100

Exemple :

1000 impressions

50 clics

CTR = 50 / 1000 × 100  
\= 5 %

Un CTR faible peut signifier :

- titre peu attractif ;
- mauvaise correspondance avec l'intention ;
- résultat peu convaincant ;
- concurrence forte ;
- mauvais ciblage.

Mais attention :

CTR seul ne permet pas de conclure.

# **C — MOTS-CLÉS, INTENTION ET RECHERCHE****C.1. Le mot-clé n'est pas le véritable objectif**

Un débutant pense :

« Quel mot-clé dois-je mettre ? »

Une meilleure question est :

**« Quelle question ou intention se cache derrière cette recherche ? »**

# **C.2. Types d'intention**

## **Informationnelle**

L'utilisateur veut apprendre.

Exemple :

comment fonctionne un moteur électrique ?

## **Navigationnelle**

Il cherche une destination précise.

Exemple :

IFRI UAC

## **Transactionnelle**

Il veut réaliser une action.

Exemple :

acheter ordinateur portable

## **Commerciale**

Il compare avant achat.

Exemple :

meilleur ordinateur pour programmation 2026

## **Locale**

Il cherche quelque chose dans une zone.

Exemple :

restaurant africain Calavi

# **C.3. Une requête peut avoir plusieurs intentions**

Exemple :

« React vs Vue »

Peut signifier :

- apprendre les différences ;
- choisir une technologie ;
- préparer un projet ;
- comparer pour un recrutement.

Il faut donc comprendre le contexte.

# **C.4. Search intent**

Le contenu doit répondre à l'intention.

Si quelqu'un cherche :

« comment installer X »

et arrive sur une page :

« achetez notre formation X »

la page peut être excellente commercialement mais mauvaise pour cette requête.

# **C.5. Recherche de mots-clés**

Elle permet notamment de découvrir :

- vocabulaire utilisateur ;
- volume de recherche ;
- concurrence ;
- variantes ;
- questions ;
- intentions.

Mais le volume ne doit pas être la seule métrique.

Une requête à faible volume mais très qualifiée peut avoir plus de valeur qu'une requête extrêmement populaire.

# **D — ARCHITECTURE DE SITE ET SEO TECHNIQUE****D.1. Architecture**

Une bonne architecture facilite :

- navigation humaine ;
- compréhension du site ;
- découverte des pages ;
- liens internes ;
- maintenance ;
- évolutivité.

Exemple :

/  
├── services/  
│ ├── transport/  
│ ├── livraison/  
│ └── location/  
├── blog/  
│ ├── guide-a/  
│ └── guide-b/  
└── contact/

# **D.2. Architecture plate vs profonde**

### **Plate**

Accueil  
↓  
Page

### **Profonde**

Accueil  
↓  
Catégorie  
↓  
Sous-catégorie  
↓  
Sous-sous-catégorie  
↓  
Page

Une profondeur excessive peut compliquer :

- navigation ;
- maintenance ;
- découverte.

Mais « tout mettre à la racine » n'est pas automatiquement meilleur.

# **D.3. URLs**

Une bonne URL devrait être :

- compréhensible ;
- stable ;
- cohérente ;
- descriptive lorsque pertinent.

Mieux :

/transport-marchandises

que :

/page?id=7382

Mais une URL descriptive n'est pas une formule magique de classement.

# **D.4. Canonical**

La balise canonical indique quelle URL représente préférentiellement une page lorsqu'il existe plusieurs URLs similaires ou équivalentes.

Exemple conceptuel :

<link  
rel="canonical"  
href="https://example.com/produits/chaussures"  
/>

Important :

canonical n'est pas une redirection.

# **D.5. Redirection**

Une redirection indique qu'une URL doit conduire vers une autre.

Exemple classique :

ancienne-page  
↓  
301  
↓  
nouvelle-page

Utile notamment lors :

- migration ;
- changement d'URL ;
- restructuration.

# **D.6. Robots.txt**

Le fichier :

/robots.txt

permet de communiquer certaines règles aux crawlers.

Exemple conceptuel :

User-agent: \*  
Disallow: /admin/

Mais :

**robots.txt n'est pas un mécanisme de sécurité.**

Il ne doit jamais servir à protéger des données sensibles.

# **D.7. Sitemap XML**

Un sitemap fournit une liste structurée d'URLs que tu souhaites signaler aux moteurs.

Exemple :

https://example.com/sitemap.xml

Il est particulièrement utile pour :

- grands sites ;
- sites complexes ;
- nouveaux contenus ;
- architectures difficiles à explorer.

Mais :

mettre une URL dans un sitemap ne garantit pas son indexation.

# **D.8. Liens internes**

Les liens internes relient les pages d'un même site.

Ils servent notamment à :

- navigation ;
- découverte ;
- architecture ;
- contexte ;
- distribution interne de signaux.

Exemple :

Article  
↓  
Guide principal  
↓  
Page service

# **D.9. Texte d'ancrage**

Le texte cliquable d'un lien.

Mauvais contexte :

Cliquez ici.

Plus descriptif :

Consultez notre guide du transport international.

Le texte doit être naturel et réellement décrire la destination.

# **E — CONTENU ET SÉMANTIQUE****E.1. Écrire pour l'utilisateur avant d'écrire pour Google**

Un contenu SEO réussi doit d'abord répondre à :

**Pourquoi quelqu'un aurait-il besoin de cette page ?**

# **E.2. Structure d'une page**

Une page peut avoir :

H1  
├── Introduction  
├── H2  
│ ├── H3  
│ └── H3  
├── H2  
└── H2

Les headings structurent le contenu.

# **E.3. H1**

Le H1 représente généralement le titre principal visible de la page.

Il doit être cohérent avec le sujet.

Il ne faut pas chercher à mettre 30 mots-clés dans un H1.

# **E.4. Entités**

Un concept plus avancé :

une entité représente une chose identifiable : personne, organisation, lieu, produit, concept, événement, etc.

Exemple :

"IFRI"

peut correspondre à une organisation spécifique.

Comprendre les entités aide à comprendre pourquoi le SEO moderne dépasse le simple comptage de mots.

# **E.5. Sémantique**

Un contenu sur :

transport routier

peut naturellement évoquer :

- camion ;
- logistique ;
- livraison ;
- fret ;
- itinéraire ;
- chauffeur ;
- marchandises.

Cela construit un contexte thématique.

Mais attention :

**ne pas transformer cela en bourrage de mots-clés.**

# **E.6. Keyword stuffing**

Répéter artificiellement :

transport Calavi  
transport Calavi  
transport Calavi  
meilleur transport Calavi  
transporteur Calavi

n'est pas une stratégie saine.

La question est :

**le contenu est-il réellement utile et naturel ?**

# **E.7. Contenu original**

Une page qui reformule simplement dix autres pages apporte peu de valeur.

L'originalité peut venir de :

- expérience réelle ;
- données ;
- tests ;
- comparaison ;
- expertise ;
- exemples ;
- cas pratiques ;
- perspective locale ;
- outils ;
- démonstrations.

# **E.8. E-E-A-T**

Google utilise notamment les notions :

- Experience ;
- Expertise ;
- Authoritativeness ;
- Trustworthiness.

Ce n'est pas un bouton magique à activer.

Il s'agit plutôt d'un cadre permettant de réfléchir à la crédibilité du contenu.

# **F — DONNÉES STRUCTURÉES ET RICH RESULTS****F.1. Pourquoi les données structurées ?**

HTML :

présente le contenu.

Données structurées :

fournissent aux machines une représentation plus explicite de certaines informations.

Exemple :

Article  
Produit  
Organisation  
LocalBusiness  
Événement  
Recette  
Vidéo

# **F.2. Schema.org**

Schema.org fournit un vocabulaire de données structurées largement utilisé sur le Web.

Un format courant est :

JSON-LD

Exemple simplifié :

{  
"@context": "https://schema.org",  
"@type": "Organization",  
"name": "Exemple",  
"url": "https://example.com"  
}

# **F.3. Rich Results**

Certaines données structurées peuvent rendre une page éligible à des fonctionnalités enrichies dans les résultats.

Mais :

**éligible ≠ garanti.**

C'est une distinction fondamentale.

# **F.4. Ne pas ajouter des données structurées mensongères**

Si ton site n'est pas réellement :

- un restaurant ;
- un produit ;
- un événement ;

ne lui attribue pas artificiellement ces types simplement pour obtenir une apparence enrichie.

# **F.5. FAQ et évolution des fonctionnalités**

Il faut être particulièrement prudent avec les vieux tutoriels SEO.

Certaines fonctionnalités de résultats enrichis disparaissent ou changent.

Par exemple, les FAQ rich results ont fait l'objet d'un retrait de la recherche Google en 2026.

Donc :

**un tutoriel SEO vieux de trois ans peut aujourd'hui être techniquement dépassé.**

# **G — SEO LOCAL**

Pour un produit comme :

restaurant à Calavi

le référencement local devient très important.

# **G.1. Google Business Profile**

Pour une entreprise physique, il faut travailler :

- nom ;
- catégorie ;
- adresse ;
- téléphone ;
- horaires ;
- site ;
- photos ;
- avis ;
- informations cohérentes.

# **G.2. NAP**

Concept classique :

Name — Address — Phone

Les informations doivent rester cohérentes entre les différentes présences de l'entreprise.

# **G.3. Pages locales**

Exemple :

/restaurant-calavi  
/restaurant-cotonou  
/restaurant-porto-novo

Mais uniquement lorsque ces pages correspondent à de véritables offres/localités.

Créer artificiellement 100 pages presque identiques uniquement pour capter des villes peut produire un site pauvre.

# **G.4. Avis**

Les avis peuvent jouer un rôle important dans la confiance utilisateur et la présence locale.

Mais :

ne jamais fabriquer artificiellement des avis.

# **H — IMAGES, VIDÉOS ET AUTRES TYPES DE CONTENU****H.1. Images**

Pour chaque image importante :

- format approprié ;
- dimensions adaptées ;
- compression ;
- nom cohérent ;
- alt approprié lorsqu'il est nécessaire ;
- contexte textuel ;
- lazy loading lorsque pertinent.

# **H.2. Alt text**

Le alt sert principalement à fournir une alternative textuelle lorsqu'une image ne peut pas être perçue.

Mauvais :

alt="image123.jpg"

Meilleur :

alt="Camion de livraison devant un entrepôt à Calavi"

Mais il ne faut pas non plus transformer chaque alt en liste de mots-clés.

# **H.3. Images trop lourdes**

Une image de 5 Mo utilisée comme simple illustration peut ralentir inutilement une page.

Il faut réfléchir :

Qualité visuelle  
↕  
Poids  
↕  
Dimensions  
↕  
Format

# **H.4. Vidéo**

Une vidéo peut être très lourde.

Questions :

- est-elle nécessaire ?
- doit-elle être chargée immédiatement ?
- peut-elle être différée ?
- quelle miniature utiliser ?
- quel impact sur LCP ?
- quelle consommation mobile ?

# **I — WEB PERFORMANCE : COMPRENDRE CE QUI REND UN SITE RAPIDE****I.1. Performance ≠ simplement « temps de chargement »**

La performance moderne est multidimensionnelle.

Elle concerne :

- chargement ;
- affichage ;
- interactivité ;
- stabilité visuelle ;
- réseau ;
- CPU ;
- mémoire ;
- taille des ressources ;
- rendu ;
- expérience réelle.

# **I.2. Le parcours d'une page**

Simplifions :

URL  
↓  
DNS  
↓  
Connexion  
↓  
Serveur  
↓  
HTML  
↓  
CSS / JS / Images  
↓  
Parsing

CSSOM

↓

↓

Comprendre cette chaîne change complètement ta manière de diagnostiquer les performances.

# **I.3. DNS**

Avant de contacter ton serveur, le navigateur doit notamment résoudre le nom de domaine vers une adresse IP.

Une résolution lente peut contribuer au temps initial.

# **I.4. HTTP**

Le navigateur communique avec le serveur via HTTP/HTTPS.

Concepts importants :

- requête ;
- réponse ;
- headers ;
- status codes ;
- cache ;
- compression.

# **I.5. CDN**

Content Delivery Network.

Au lieu de servir toutes les ressources depuis un seul emplacement :

Utilisateur  
↓  
Serveur distant unique

on peut distribuer des ressources via des points de présence plus proches.

CDN  
/ | \\  
↓ ↓ ↓  
Afrique Europe Amérique

# **I.6. Cache**

Le cache permet d'éviter de recalculer ou retélécharger certaines ressources.

Types :

- navigateur ;
- CDN ;
- serveur ;
- application ;
- base de données.

# **I.7. Compression**

On peut réduire la taille des ressources.

Technologies :

- gzip ;
- Brotli ;
- compression moderne selon environnement.

# **I.8. Minification**

Réduction de caractères inutiles dans :

- CSS ;
- JavaScript ;
- HTML.

Mais attention :

minifier un mauvais code ne transforme pas une mauvaise architecture en bonne architecture.

# **I.9. Code splitting**

Au lieu de charger tout le JavaScript :

Application entière  
↓  
1 gros bundle

on peut diviser :

Accueil  
↓  
code nécessaire  
<br/>Dashboard  
↓  
code nécessaire  
<br/>Admin  
↓  
code nécessaire

# **I.10. Lazy loading**

Charger certaines ressources uniquement lorsque nécessaire.

Exemple :

Page  
↓  
contenu visible immédiatement  
↓  
ressources secondaires  
↓  
chargement différé

# **I.11. SSR, CSR, SSG**

Trois concepts essentiels.

## **CSR**

Client-Side Rendering.

Le navigateur construit une grande partie de l'interface avec JavaScript.

## **SSR**

Server-Side Rendering.

Le serveur génère le HTML initial.

## **SSG**

Static Site Generation.

Les pages sont générées à l'avance.

# **I.12. Comparaison**

|     |     |     |
| --- | --- | --- |
| **Approche** | **Force** | **Limitation** |
| CSR | interactivité riche | dépendance au JS initial |
| SSR | HTML initial rapide/accessible selon architecture | coût serveur/complexité |
| SSG | très performant pour contenu stable | moins adapté à certains contenus très dynamiques |
| Hybride | flexibilité | complexité supérieure |

Le choix dépend du produit.

# **J — CORE WEB VITALS**

Les Core Web Vitals sont particulièrement importants pour comprendre l'expérience réelle.

Les métriques actuelles importantes incluent :

### **LCP**

**Largest Contentful Paint**

Mesure approximativement la rapidité avec laquelle le principal contenu visible est rendu.

Question :

« Quand l'utilisateur voit-il le contenu principal ? »

### **INP**

**Interaction to Next Paint**

Mesure la réactivité après les interactions.

Question :

« Lorsque l'utilisateur agit, l'interface réagit-elle correctement et rapidement ? »

### **CLS**

**Cumulative Layout Shift**

Mesure la stabilité visuelle.

Question :

« Les éléments se déplacent-ils de manière inattendue pendant le chargement ? »

Un site peut obtenir un bon score de laboratoire et rencontrer des problèmes chez les utilisateurs réels.

Ce sont des garde-fous.
